# Type-A 参数准入：v0.6.1

生成和导入参数现在经过同一纯 Go 检查，之后才把参数文本交给 PBC 的
`NewPairingFromString`。直接调用 `core.NewContext` 也不能绕过这一层。
加密公式、公开参数的有效编码、用户取样、策略、撤销和缓存算法未更改。

## 检查的实际内容

- 文件长为 1 字节至 1 MiB；只允许可打印 ASCII 及空格、制表符、CR/LF。
- 精确包含 `type/q/h/r/exp2/exp1/sign1/sign0` 八个字段；拒绝重复、缺失、
  未知字段、注释和非规范整数。字段顺序可以不同。
- 采用 Type A；`q,h,r` 为正数，整数至多 16384 位；`3 < r < q`，
  `0 < exp1 < exp2 <= 16384`，两个符号均为 `1` 或 `-1`。
- 精确检查 `r = 2^exp2 + sign1*2^exp1 + sign0`、`h*r = q+1`，以及
  `h` 可被 12 整除。这是本原型支持的官方 Type-A 参数配置，
  不声称所有其他数学配置都不可能。
- 对 `q,r` 分别调用 Go 的 `ProbablyPrime(64)`；检查群阶大于本次最大容量加一。
  后者也由核心 Setup 的容量条件维护。

依据为 [PBC 官方 Type A 内部说明](https://crypto.stanford.edu/pbc/manual/ch08s03.html)
及 PBC 0.5.14 `ecc/a_param.c` 的参数加载、曲线初始化与 Miller 循环代码。
原来的“两个数通过可能素数检查且配对类型对称”不能推出上述等式。
例如保留原 `q,r` 而把 `h` 加 12，旧的数值前置检查仍通过，
新检查会在调用原生参数解析前拒绝。没有把该情况描述为已执行的密码攻击。

## 回传与成本

新运行标识是 `chare-go-pbc-v0.6.1`。`manifest.json` 的
`parameters.admission` 记录检查配置，原始 `parameters.txt` 保持不变，
其哈希仍绑定确切文件字节。`probable_prime_rounds:64` 表示传入 Go API 的参数，
不是实际执行次数的测量值；小数值和筛除分支可能提前结束。

Python 导入会独立重算上述整数恒等式、规范解析、参数哈希、位长和容量条件，
并核对新版检查报告。缺少报告或报告与文件不一致时拒绝进入汇总。
Python 没有重新证明素性；完整性校验也不是第三方实验真实性证明。
旧版运行仍可导入，但不会追认它执行了新版检查。

检查有真实开销：初次参数准备的计时包含准入工作，每次新的核心上下文也重新
检查。后者位于当前局部协议计时之外；不能因此认为它免费或将局部区间总和
当作完整进程时间。此次没有新增网络群点反序列化接口。

## 安全边界

这不是具体安全强度认证。`ProbablyPrime` 是可能素数接口，不能用其轮数对
专门构造的恶意大整数宣称确定的素性或统一的伪通过概率。参数来源仍须可信，
正式实例需要单独落实素性、子群/配对实现和具体曲线的安全依据。
当前测试参数、256/1536 配置和同名义参数对照均不自动成为 128 位安全实例。
本修正不改变论文的 GBGM＋ROM 定理，也不构成新的密码学贡献。
