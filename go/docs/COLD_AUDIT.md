# 独立冷审计与全员实测

v0.6.0 新增 `typed-public-history-replay-v1`。已有的普通首次获取仍使用认证聚合服务；本项是主更新负载结束后的独立压力边界，不能与首次获取重复相加或称为默认部署开销。

## 实际流程

CHARE 冷客户端只有指定公共参数、固定的认证公钥、当前序号、完整根证书、全部发行历史、当前签名快照和自己的帮助材料。验证器不接收用户私钥、资格真值、发行掩码、签名私钥或目录矩缓存。它实际：

1. 验证当前快照签名和完整根证书、全部根投影。
2. 从公开的原始发行记录识别命名空间，验证每条旧／新记录的完整投影、胶囊签名及绑定。
3. 按原顺序重新建立初始聚合，再逐条重放更新，保留初始身份和追加式上下文。
4. 将独立重建结果序列化成当前快照，与收到的签名字节完全比较，并使用重建值验证本客户端的帮助。
5. 实际序列化及复制完整快照、签名、全部历史记录与帮助，记录这些字节。已经在快照中出现的重复字段不被免费删去。

外部当前序号与认证根仍是信任前提。这不是分叉检测、现实资格审查或恶意网络编码解析器。输入仍是同一 PBC 上下文的生成类型对象；冷审计从这些公共对象重放，不能据此声称已提供网络服务。

source-DH 对照为每个冷客户端实际重验自己的完整公开目录、证书、当前授权 epoch 与各策略名单、成员公钥对应，并序列化／复制该独立数据包。其当前授权名单仍由外部指定，不能自行验证隐藏资格语义；不强迫它下载 CHARE 历史或投影数组。

## 范围与计费

`workload.cold_audit_all_users=true` 实际执行每个槽位的冷审计；`false` 或省略只执行槽位 0。`config/sanity.json` 和非默认 `config/paper-full.json` 设为 true；有界默认 `config/paper.json` 设为 false。默认无参数配置仍保留单客户端范围，实际选择写入 manifest 与逐案例配置。可以选择单客户端配置，但不能把它当成全员测量。

每个客户端、每个方案分别产生 `count=1` 的计时行和带槽位身份的完成记录。包括 CHARE 实际生成所需帮助的服务端工作；不是纯客户端 CPU 时间。序列化复制不代表真实网络时延。Python 会核对完整客户端覆盖、当前序号、实测行与负载字节，并另外输出 `cold_audits.csv`；不以单次计时乘以人数。

“冷”指客户端没有先前验证好的目录状态。批处理在同一进程/PBC 上下文中按槽位顺序执行，各自重新构建公开验证状态；它不是 N 台独立设备或 N 次操作系统/CPU 缓存冷启动。公共参数和原生库状态可复用，验证结果不跨客户端免费复用。

满槽 N、m 个属性和 T 次主更新时，CHARE 实际验证的历史记录数为 `u=mN+T`。当前显式验证算法每客户端执行

`2(N+u)(N-1)+2(m+3)` 次配对。

第一项验证根与所有历史投影，第二项验证一个完整帮助。全部客户端均冷启动时，程序实际重复这些操作 N 次；公式只核对操作计数，不用于伪造时间。全量历史重放与下载可能很重。非默认 paper-full 保留原范围；默认 paper 使用明确记录的较小容量和单客户端审计，绝不把外推当作全员实测。

此前 v0.5.1 及更旧的 `stress_one_client` 行仅为一个客户端的签名／当前记录检查，没有本项独立历史重放与聚合核对。旧数据保持原范围，不能与 v0.6.0 合并为重复样本。
