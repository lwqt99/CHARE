# 原生群实例准入

2026-11-06 的完整测试曾在原 CHARE 小群夹具中报告 `generator sampling failed`。
失败日志已保留。追查原始 PBC 0.5.14 `ecc/curve.c` 得到具体原因：

1. `field_init_curve_ab` 只生成一次内部点，并乘余因子得到缓存基点。
2. 这个缓存点可能恰为单位元。
3. `curve_random_pointmul` 每次随机取标量后乘的是同一个缓存基点，因此
   对这个原生实例重试 1024 次也全是单位元；它们不是独立的均匀群抽样。

定向测试在真实原生库中只强制第一次坐标取样为零，产生曲线上的 `(0,0)`，
随后恢复真实随机源。偶数余因子将该点变成单位元，之后的 1024 次随机点
确实全为单位元。测试用的随机源不进入正式代码。最初测试夹具错误地强制
每次坐标取样为零，导致原生非二次剩余搜索超时；该失败日志同样保留，
没有当作修复后的成功证据。

## 修复位置与分布

`internal/nativegroup` 在任何协议设置秘密产生**之前**检查原生群实例。
对每个源群最多进行 32 次非零探测；若不可用，只用**同一个公开参数文本**
重新初始化原生对象，最多 8 次。耗尽则明确失败。Type A 检查一个源群，
Type F 检查两个不同源群。没有重新生成曲线参数，也没有重新索取协议 CRS。

在已认可的素数阶源群中，只要缓存基点非零，PBC 后续以独立均匀标量乘它
就产生均匀群点；非零探测证明该缓存点不为零。协议自己的生成元取样、
全域/非零标量取样、一次源设置及失败规则继续执行，算法和线格式不变。
两方案在同样的原生准入层上运行；没有添加安全性哈希或知识假设。

原生初始化次数、拒绝次数和探测次数都记录在上下文的 `NativeAdmission`。
主批量案例的 `result.json` 新增 `native_context`，保存实际初始化耗时和
成功后的计数，失败则保存错误；它是双方共享的原生环境费用，不重复分配
给两个方案。既有 `raw.csv` 的每方案协议区间与字节值没有改变定义。
当前绘图不会自动把这个新共享字段加进单方案汇总；写完整运行费用时必须
单独列出它，不能认为它为零或混入旧结果。旧数据没有这项测量。

上述上限限制的是包装层重试；不承诺原生 C 调用内部的硬实时上限。原生
库、熵源、可信参数和平台算术仍需独立正确。没有把原生错误概率混入消息
保密界，也不以这些功能测试代替密码学证明。

CHARE 协议仍标识 v0.6.2，本次是附加开发交付，完整源码哈希区别于旧实测
版本。不能把旧批量数据重新标注成包含本次准入和 RIPE 核心的数据。
